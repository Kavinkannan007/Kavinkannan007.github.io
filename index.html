Referral routing and policy checks

CasePilot

The problem

Caseworkers need a consistent way to triage incoming referrals. Before acting, they need the resident’s history, the policy that applies, and a clear record of decisions already made.

Python · Streamlit · REST APIs · JSON · Policy engine

How I built it

  1. I connected intake to resident history

    I built the referral workflow so it retrieves the resident’s history before triage. Passing that context through the workflow lets each stage operate on the same case.

  2. I put policy checks before routing

    I added a policy engine that evaluates proposed actions before a referral moves on. If an action is outside the rules, the workflow blocks it and prepares the case for human review.

  3. I made escalations traceable

    I isolated failures by referral and logged the steps taken on each case. I included those details in the escalation package so a caseworker can pick up where automation stopped.

Failed-payment recovery and audit trails

Recovery Sentinel

The problem

When a payment fails, the operations team needs to know why it failed and whether a retry makes sense. They also need to see how a recovery decision was reached.

Python · SQLite · Streamlit · Groq · Pandas · pytest · Git

How I built it

  1. I separated classification from recovery

    I built a Python pipeline that classifies the cause of a failure before choosing a recovery action. I integrated Groq for classification and added validation and fallback handling for unsuitable responses.

  2. I simulated retries and recorded decisions

    I implemented retry simulation and stored decisions in SQLite. I included an escalation path for cases that need a person to decide what happens next.

  3. I built a review dashboard and tested the workflow

    I brought decisions and audit events into a Streamlit dashboard so an operator could inspect a run. The reported run covered 134 failed payments and produced 803 audit records. All 93 tests passed.

From a resident’s report to a live status update

Civic Issue Reporting System

The problem

A resident reporting a local problem needs to show what happened and where. The service team needs to route the report, update it securely, and let the resident follow its progress.

Java · Spring Boot · React · MySQL · JWT · WebSockets · REST APIs

How I built it

  1. I built the reporting flow

    I created a React interface for submitting a description, a photo, and a location together. That gives the team reviewing a report enough context to identify the issue.

  2. I connected the interface to protected APIs

    I built the Spring Boot APIs, stored reports in MySQL, and used JWT authentication with role-based permissions. I integrated classification to help group incoming reports by issue type.

  3. I delivered status updates to residents

    I used WebSockets to send status changes back to the interface. Residents can follow an existing report as it moves through the system.

Website risk review and browser alerts

HostHunter

The problem

A warning about a suspicious website gives a visitor little context on its own. Reviewers need a place to inspect the available signals and understand what triggered concern.

Python · Flask · React · PostgreSQL · Scikit-learn · Censys API · Mapbox · Tailwind CSS

How I built it

  1. I gathered website observations

    I connected website metadata and hosting information to a historical record. That gave the review interface context beyond a single observation.

  2. I built the analyst dashboard

    I brought risk signals, historical tracking, and geographic context into a React dashboard. I integrated Mapbox so reviewers could explore the available hosting information on a map.

  3. I surfaced warnings in the browser

    I built a Chrome extension to display alerts for potentially unsafe websites and let users review recently visited URLs. The dashboard supports a deeper investigation when a warning needs follow-up.
