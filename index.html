Referral routing and policy checks

CasePilot

A referral needs more than a destination. The receiving caseworker needs the resident’s history, the rule that determined the route, and a record of the actions already taken.

Python · Streamlit · REST APIs · JSON · Policy engine

  1. Assemble the case

    The workflow ingests a referral and retrieves the associated resident history before triage. Keeping that context attached to the referral gives later steps a common record to work from.

  2. Evaluate the policy

    A policy engine checks whether a proposed action is allowed. The workflow uses those checks to route the case or prepare an escalation when a person needs to make the decision.

  3. Make the handoff reviewable

    Failures are isolated at the referral level. An escalation package and audit log let a reviewer reconstruct the execution trace and investigate the affected case.

Failed-payment recovery and audit trails

Recovery Sentinel

A failed payment creates two separate questions: what went wrong, and what should the operations team do about it? This project keeps classification, recovery decisions, and review as distinct steps.

Python · SQLite · Streamlit · Groq · Pandas · pytest · Git

  1. Classify the failure

    The pipeline processes failed-payment records and uses Groq to help classify the cause. Validation and fallback handling give the workflow a way to continue when a generated response is unsuitable.

  2. Simulate the recovery

    Recovery logic chooses a next step and simulates retries. Cases needing judgment can be escalated to a human. SQLite holds the record of the decisions for later inspection.

  3. Inspect the run

    A Streamlit dashboard brings recovery decisions and audit history together. The supplied project run covered 134 payment failures, produced 803 audit records, and passed all 93 tests.

From a resident’s report to a live status update

Civic

A resident can describe a local problem, but a service team also needs to know where it is, what category it belongs to, and who is allowed to update it.

Java · Spring Boot · React · MySQL · JWT · WebSockets · REST APIs

  1. Capture the issue

    The React interface collects a description, location and photo. Those details travel with the report so a team reviewing it can understand both the problem and where to find it.

  2. Control changes

    Spring Boot exposes the reporting APIs, with JWT authentication and role-based permissions controlling access. AI-assisted classification helps group incoming reports, while MySQL stores their records.

  3. Close the feedback loop

    When the status changes, WebSockets carry the update to the interface. A resident can follow the same report over time instead of submitting it again to ask what happened.

Website risk review and browser alerts

HostHunter

A browser warning is more useful when an analyst can inspect the evidence behind it. HostHunter connects the alert shown to a visitor with a dashboard for reviewing the website’s history and risk signals.

Python · Flask · React · PostgreSQL · Scikit-learn · Censys API · Mapbox · Tailwind CSS

  1. Collect observations

    The backend gathers website metadata and historical observations. Keeping observations together gives a reviewer context beyond the most recent alert.

  2. Present the evidence

    A React dashboard combines historical tracking, risk scores and geolocation. An analyst can compare signals and inspect their geographic context in a single review surface.

  3. Bring the warning to the visitor

    A Chrome extension surfaces alerts for potentially unsafe sites and lets the user review recently visited URLs. The extension and dashboard serve different audiences using the project’s risk information.
